# 扩展生态与应用层功能 —— SillyTavern 行为清单

调研对象：本地 SillyTavern 1.18.0。行为语义记录，不含 AGPL 代码复制。

JavaTavern 现状（已核实）：无正则脚本、无快捷回复、无 STscript、无工具调用、无向量检索、无 TTS/生图/翻译/图片描述扩展。有一个极简的本地 Agent 命令系统（`LocalAgentRouter`，`/clear` 式确认后执行）。

---

## 1. 内置扩展逐项评估

| 扩展 | 做什么 | 服务端依赖 | 移动端可行性 | 复杂度 |
|---|---|---|---|---|
| **正则脚本** | 查找替换文本，可分别只影响"展示"或"发送给模型"，按位置（用户输入/AI输出/世界书/推理块）生效，支持深度范围 | 无，纯客户端 | 直接可做 | M |
| **快捷回复** | 用户自定义命令按钮工具栏，绑定 STscript，支持多种自动触发时机 | 无 | 直接可做 | L（全量）/ M（去掉自动触发和世界书联动的精简版） |
| **总结/长期记忆** | 定时/按字数阈值自动生成对话摘要并注入 prompt，替代旧摘要 | 无（用主模型本身生成） | 直接可做，且跟 JavaTavern 已有的"用户确认长期记忆"概念高度重合 | M |
| **向量检索** | 语义检索历史消息/文件/世界书条目，而非纯关键词匹配 | 云端 embedding API 可直连，本地模型需要设备端推理 | 云端 embedding 部分可做 | L（完整）/ M（仅聊天记录 RAG + 单一云端 embedding 来源 + 暴力余弦相似度） |
| **数据银行/附件** | 给聊天/角色/全局挂文件，PDF/HTML/Markdown/EPUB/Office 文档自动转文本 | 部分（网页/Wiki 抓取需服务端） | 本地文件上传+转文本可做，抓取类要看情况 | M（基础）/ L（全格式转换器） |
| **工具调用** | 解析 API 返回的 `tool_calls`，本地执行，把结果喂回去 | 无 | 直接可做，且跟 JavaTavern 已有的 Agent 命令系统天然互补 | M |
| **图片描述** | 给不支持视觉的模型"看图"能力 | multimodal 模式无需服务端（复用已有视觉模型调用），local/extras/horde 需要 | multimodal 模式直接可做 | S |
| **表情/立绘** | 按当前消息情绪切换角色立绘图片 | LLM 分类模式无需服务端 | LLM 分类模式可做 | M |
| **图库** | 按角色浏览/管理生成或上传的图片 | 无（本地文件存储） | 直接可做 | S–M |
| **图片生成** | AI 主动或用户手动触发生图，插入聊天 | 部分（云端 provider 可直连，ComfyUI/DrawThings 需局域网） | 云端 provider（DALL-E/NovelAI/Stability/Pollinations）可直连 | L（全量）/ S–M（1-2 个云端 provider + 基础模式） |
| **TTS 朗读** | 朗读消息 | 部分（云端 provider 直连，本地 WASM 模型不可行） | Android 自带 TTS 引擎是"System 模式"的天然替代品，加 1-2 个云端 provider | S |
| **翻译** | 消息双向机器翻译 | 部分（Google/DeepL 等有公开 REST API） | 1-2 个 provider 可做 | M |
| **STscript** | 内置脚本语言，快捷回复/世界书自动化的底层 | 无 | 一个精简解释器（管道链、命名/位置参数、`/if`、变量、十几个聊天命令）足够覆盖多数用例 | M（精简子集）/ L（完整） |
| **多用户账号** | 服务端多租户 | — | 手机应用天生单用户，不适用；顶多做"App 锁屏密码" | 不适用 |
| **连接配置档案** | 见 [api-connections.md](api-connections.md) §4 | — | — | — |

## 2. 移动用户最可能想念的功能（按调研给出的排序，附一句话理由）

1. **正则脚本**——几乎所有认真用 SillyTavern 的人都至少挂一个正则（隐藏OOC吐槽、清理模型怪癖），没有这个很多角色卡的预期效果会跑偏。
2. **快捷回复**——重度用户的自动化工作流入口，没有等于丢了整个工具栏。
3. **总结/长期记忆**——跟 JavaTavern 已规划的功能直接重合，用户会默认期待"自动"而不只是"手动确认"。
4. **向量检索**——长对话用户靠这个让旧剧情"记得住"而不必每轮都占满上下文。
5. **数据银行/文件附件**——上传一份 PDF 设定集当上下文是常见的世界观搭建工作流。
6. **工具调用**——越来越多模型原生支持，没有这个等于"AI 主动生图"之类的智能体行为直接失效。
7. **图片生成**（至少 1-2 个云端 provider）——角色"发自拍"是 SillyTavern 区别于纯聊天应用的招牌体验之一。
8. **TTS**（Android 原生引擎 + 1-2 个云端 provider）——长时间/解放双手场景下的高频需求。
9. **连接配置档案**——同时用多个 API/模型的用户默认期待一键切换而不是重新填一遍。
10. **表情/立绘（LLM 分类模式）**——视觉小说式头像切换，重度角色卡用户很吃这个。
11. **STscript 核心命令集**——快捷回复、世界书自动化、导入卡片里嵌的命令都靠它打底，缺了会导致部分卡片"看起来坏了"。
12. **主题/气泡与扁平两种聊天显示 + 自定义强调色**——纯观感，但社区里偏好很强烈，JavaTavern 目前正好在投入这块。
13. **设置/聊天备份与恢复**——App 崩溃或误操作丢聊天记录是最伤感情的体验之一。
14. **密钥管理器（带安全存储）**——"我的 key 不会泄露"是信任的基础；JavaTavern 的 Android Keystore 方案在这点上已经优于 ST 的服务端方案，只是缺"一种 key 存多把"的结构。
15. **聊天翻译**（1-2 个 provider）——非英语用户群体的硬需求，不是可选项。

## 3. 具体实现要点（挑几个值得展开的）

### 正则脚本
字段：`findRegex`（`/pattern/flags`）、`replaceString`（支持 `{{match}}` 和捕获组）、`trimStrings[]`、`placement[]`（用户输入/AI输出/世界书/推理块，一个脚本可以同时作用于多个位置）、`markdownOnly`（只影响展示，不影响发给模型的内容）/`promptOnly`（反之）、`minDepth`/`maxDepth`（只在最近N轮生效）、`runOnEdit`。三种作用域：全局、角色卡自带（需要用户显式"允许"才生效，防止导入卡片时被动注入脚本——这是个值得照抄的安全设计）、预设自带。

### 快捷回复
一个"快捷回复"=图标/文字标签+绑定的脚本命令。可以设成"自动发送"或"插入到输入框待编辑"。自动触发时机很多（启动时/用户发消息后/AI回复后/切换聊天时/生成前），JavaTavern 精简版建议只做"手动点击"，自动触发和世界书联动放后面。

### 工具调用
核心是"解析 API 返回的 `tool_calls` 字段 → 本地按名字匹配一个已注册的函数 → 执行 → 把结果作为一条新消息喂回去 → 再生成一次"，循环直到模型不再请求工具或达到递归上限。三种响应形状要适配：OpenAI 式 `tool_calls[]`、Claude 的 `content_block` `type:'tool_use'`、Google 的 `functionCall` part。JavaTavern 现有的 `LocalAgentRouter`/`ChatAgentController`（本地指令+确认执行）可以直接扩展成这套"工具"的一种——本地命令本来就是一种"工具"，两者是同一个抽象的不同实例。

### 向量检索（精简版）
聊天记录 RAG 的最小可行版本：选定一个云端 embedding provider（如 OpenAI `text-embedding-3-small`），新消息生成时异步计算并存 embedding（SQLite BLOB 列存浮点数组），检索时对最近 N 条以外的历史消息做暴力余弦相似度计算取 top-K（移动端聊天记录规模下暴力搜索完全够用，不需要专门的向量索引库），按配置的位置/深度插入 prompt。

## 4. 应用层功能（不算"扩展"，但同属这次调研范围）

- **主题/UI 定制**：头像形状（圆/圆角方/方）、聊天显示模式（气泡 vs 扁平）、字号缩放、减少动画（可跟随系统"减弱动态效果"设置）——JavaTavern 最近的视觉改版工作正好覆盖这块，方向一致。
- **多语言**：ST 自带 17 种语言的字符串文件；Android 自己的字符串资源系统就是等价机制，只是内容需要翻译，机制上不需要额外设计。
- **密钥安全存储**：Android EncryptedSharedPreferences/Keystore 严格优于 ST 的服务端方案，JavaTavern 已经在用；缺的是"一种 key 类型存多把+按标签选择"的数据结构。
- **最近聊天/置顶**：首页最近打开的聊天列表 + 收藏置顶——JavaTavern 现在首页已经是角色列表，加一层"最近/置顶"排序即可，不需要新实体。
- **快捷键/无障碍**：移动端意义不大（IME 发送键本身就是"回车发送"），可以跳过 ST 这部分的桌面端设计。
- **第三方扩展安装机制**：需要打包 JS 引擎（WebView/QuickJS）+ 暴露稳定扩展 API，工作量大且收益存疑——**不建议做**，如果要扩展性，走原生插件机制而不是照抄 ST 的 JS 扩展安装器。

## 5. 明确不建议做的部分

- 多用户账号（移动端场景不适用）
- 第三方 JS 扩展安装机制（成本远超收益）
- NovelAI/AI Horde 专属参数（如硬编码的分模型封禁词表）——这些是 NovelAI 自己模型的特化调优，不影响其作为一个"能跑"的 Chat Completion 来源
- 本地 WASM 模型（表情分类器/图片描述/embedding 的 local 模式，TTS 的 Kokoro/Coqui-local）——设备端推理是完全不同量级的工程投入，Android 端更现实的路径是要么用云端 API，要么用 Android 系统自带能力（如系统 TTS），不要重新发明设备端 ML 推理管线
