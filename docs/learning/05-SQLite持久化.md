# 专题 05：SQLite 持久化

## 统一数据库

`TavernDatabase` 当前统一保存：

- 角色、角色 Prompt、来源哈希和世界书条目；
- 私聊/群聊消息、Agent 审计与 FTS；
- 生成参数预设和群聊成员关系。

角色卡导入在事务中写角色和世界书；`source_hash` 唯一约束避免重复导入。首次创建统一数据库时会读取旧 `characters.db` 与 `java_tavern.db`。每个迁移使用 savepoint：成功后才删除旧文件，失败则回滚并保留源文件，同时中止数据库创建，避免静默丢数据。

## 版本演进

统一数据库当前版本为 v4：

1. v1：角色、世界书、消息、Agent 审计与 FTS。
2. v2：补充世界书位置、顺序、优先级、深度、概率和递归字段。
3. v3：增加生成参数预设。
4. v4：增加群聊表以及消息的发言角色字段。

旧版本升级不能删表重建，因为用户的角色与聊天记录是产品的核心资产。

## 分页

首屏 SQL 按 `id DESC LIMIT 60` 读取后在内存反转。向上滚动执行：

```sql
SELECT ... FROM messages
WHERE character_id = ? AND id < ?
ORDER BY id DESC
LIMIT 40;
```

这是键集分页。相比 `OFFSET 10000`，数据库不需要每次先跳过前面大量记录。

## FTS

消息触发器同步 `messages_fts`。搜索先使用 FTS phrase 查询；未命中或表达式异常时退回 `LIKE`，保证中文和特殊字符仍有可用结果。点击结果后按消息 ID 读取附近上下文。

## 当前问题

- 迁移策略缺 instrumentation test 和真实旧库 fixture。
- 长期记忆仍位于私有 SharedPreferences，尚未纳入统一导出事务。
- 消息分支、摘要和备份恢复会继续增加 schema 复杂度。
- 是否迁移 Room 应由迁移测试、查询复杂度和可观察状态需求决定，而不是为了堆技术名词。
