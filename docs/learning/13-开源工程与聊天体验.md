# 13｜开源工程与聊天体验

## 这一轮解决了什么

这一轮不是继续堆“AI 功能”，而是把项目补成别人能读、能构建、愿意试用的 Android 开源工程。重点包括：连接模型、创建角色、恢复草稿、编辑消息、稳定滚动和仓库治理。

## 一、为什么要做服务预设

用户真正想完成的是“把自己的模型连上”，而不是理解 Base URL 的拼接规则。`ProviderCatalog` 把服务名称、默认地址和建议模型集中管理，设置页只负责展示和保存。

连接测试调用 `/models`，不发起生成请求。它能验证地址、鉴权和基础协议是否可用，也避免为了测试而产生一次对话费用。自定义服务仍被保留，但当前版本只接受 HTTPS。

面试时可以这样讲：

> 我把供应商差异收敛在预设层，网络层仍只依赖 OpenAI-compatible 协议。这样既降低配置门槛，也没有为每家服务复制一套聊天代码。

## 二、草稿为什么按角色保存

不同角色对应不同语境。如果全 App 只保存一份草稿，切换角色后很容易把内容发错。`ConversationDraftStore` 以角色 ID 为键，输入变化后延迟 300 ms 写入 `SharedPreferences`，发送成功前先清理对应草稿。

这里用了防抖，而不是每输入一个字符都立即写磁盘。页面销毁时还会再保存一次，降低进程切换造成的内容丢失。

## 三、为什么生成时仍允许输入

停止按钮负责控制当前流式请求，输入框负责准备下一轮内容，两者不是同一个状态。生成期间只禁用图片选择，文本输入仍保持可用，让用户不必等待模型结束后才开始组织下一句话。

## 四、为什么不能每个 token 都滚到底部

如果用户正在回看旧消息，强制滚动到底部会打断阅读。流式刷新前先判断列表是否接近底部，只有本来就在看最新消息时才继续跟随。

同时，网络线程收到的增量先进入缓冲区，每 50 ms 合并更新一次 RecyclerView，避免 token 级刷新引发频繁布局和绘制。

## 五、消息编辑和删除如何保持一致

长按普通文本消息会显示复制、编辑和删除。操作顺序是：

1. 先在数据库线程更新或删除；
2. 数据库成功后再更新 Adapter；
3. SQLite 触发器同步更新 FTS 搜索表；
4. 删除图片消息时同时清理私有文件。

这比“先改界面、数据库失败再回滚”更容易保证一致性。新消息落库后，Adapter 会把临时 ID 替换成真实数据库 ID，随后才开放持久化操作。

## 六、一个可公开仓库至少需要什么

- `README.md`：项目定位、功能、构建、隐私和路线图；
- `LICENSE`：明确别人能否使用和修改；
- `CONTRIBUTING.md`：开发和提交约定；
- `SECURITY.md`：安全问题的报告边界；
- `CODE_OF_CONDUCT.md`：协作行为约定；
- `.github/workflows/android.yml`：持续验证测试、lint 和构建；
- Issue 与 PR 模板：让反馈包含可复现信息；
- `CHANGELOG.md`：记录用户可感知的变化。

开源不等于“把代码传上去”。一个陌生贡献者应当能判断项目做什么、如何运行、数据发到哪里、改动要经过哪些检查。

## 七、你必须能回答的面试题

1. 为什么连接测试选择 `/models`，而不是发起一次聊天？
2. 为什么草稿使用 `SharedPreferences`，聊天记录使用 SQLite？
3. 为什么消息先落库再更新编辑/删除后的 UI？
4. 流式输出怎样避免频繁刷新和强制滚动？
5. API Key、角色设定、聊天内容分别存在哪里、何时离开设备？
6. 为什么只参考其他酒馆产品的能力和格式，不直接复制源码？
